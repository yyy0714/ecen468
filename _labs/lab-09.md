## Introduction

In computer architecture, a bus is a subsystem that transfers data between components inside a computer or between computers. Early computer buses were parallel electrical wires with multiple connections, but the term is now used for any physical arrangement that provides the same logical function as a parallel electrical bus. A system bus sharply reduces the number of data pins needed to connect all the devices, which is especially clear when the system includes multiple CPUs and memory devices. A typical system bus is shown in Figure 1.

![Figure 1. System Bus]({{ "/assets/files/lab09/img/1.png" | relative_url }})

*Figure 1. System Bus*

A typical system bus consists of a data bus, an address bus, and a control bus, as shown in Figure 2. The address bus specifies a physical address: when a processor or DMA-enabled device needs to read or write a memory location, it places that location on the address bus, while the value read or written travels on the data bus. The width of the address bus determines how much memory a system can address. The control bus is used by the CPU to communicate with other devices in the computer. In summary, the address bus indicates which device the CPU is communicating with, the data bus carries the actual data, and the control bus carries commands and status signals.

![Figure 2. Connections of a system bus]({{ "/assets/files/lab09/img/2.png" | relative_url }})

*Figure 2. Connections of a system bus*

Since the bus is shared among all the devices, a method for avoiding conflicts is needed. The mechanism that decides which device gets access to the bus is called **bus arbitration**. It is designed so that high-priority devices such as the processor and RAM get first access to the bus, while other devices (disks, video cards, sound cards, etc.) have lower priority and often wait until the bus is free. Several arbitration schemes exist; in this lab, we will use **centralized fixed-priority arbitration**, as shown in Figure 3.

![Figure 3. Diagram of the centralized fixed-priority arbitration]({{ "/assets/files/lab09/img/3.png" | relative_url }})

*Figure 3. Diagram of the centralized fixed-priority arbitration*

In Figure 3, there are three types of signals: `BREQ`, `BGNT`, and `BBUSY_`. A request signal (`BREQ`) is generated by a device when it wants to use the bus and is sent to the arbiter to wait for a grant. If the bus is free, the arbiter returns a grant signal (`BGNT`) to that device. If two or more requests arrive at the same time, the arbiter compares their priorities and grants only the highest-priority device. The busy signal (`BBUSY_`) indicates the status of the bus: it is high (logic `1`) when the bus is free. When a device gains the bus, it pulls `BBUSY_` low (logic `0`) while it reads from or writes to the bus, and releases it back to high when finished.

Figure 4 shows an example of bus arbitration: (1) Master 3 sends its request signal (`BREQ3`) to the arbiter while Master 1 is using the bus, so `BBUSY_` is low. (2) The arbiter sends the grant signal (`BGNT3`). (3) Master 1 completes its operation and releases `BBUSY_` (it goes high). (4) Master 3 asserts `BBUSY_` (it goes low) and begins reading from or writing to the bus.

![Figure 4. An example of bus arbitration]({{ "/assets/files/lab09/img/4.png" | relative_url }})

*Figure 4. An example of bus arbitration*

In our design, we assume the test bench has the highest priority and the UART module the lowest. As shown in Figure 2, decoders are placed between the SRAM/UART and the system bus to decode instructions from the bus. The address bus is 32 bits wide. The four most significant bits hold the device identification number (ID): the CPU (i.e., the test bench) is `0011`, the SRAM is `0001`, and the UART transmitter is `0010`. The remaining bits carry control and address signals. Figures 5 and 6 show the address maps for the SRAM and the UART.

![Figure 5. Address map to the SRAM]({{ "/assets/files/lab09/img/5.png" | relative_url }})

*Figure 5. Address map to the SRAM*
